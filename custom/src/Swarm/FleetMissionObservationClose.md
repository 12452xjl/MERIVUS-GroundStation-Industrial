## 335–339: UI entry points and per-panel review isolation

Guided's Run value comes only from the actual `StartupSeries.previousStartup`; loss of that owner yields an empty current Run, never an older initial Transaction. This is UI source integration, not an executed or verified interface.

Each panel keeps its own controller reference, lifetime epoch and frozen review token (`reviewId`, `workflowEpoch`, generation and complete context). It may approve/cancel only a still-matching review created through that same controller. A different entry's active review may be displayed as existing backend state, but is neither adopted nor cancelled. Closing, hiding, destroying or changing the controller invalidates local interaction scope and attempts cancellation only for that page's exact still-current token; cancelling a review does not end monitoring or flight, and cannot undo an already committed effect.

New reviews start with all three confirmations unchecked; controller/token changes or loss of the panel's own-review match clear them. The dialog initially focuses its explicit close/cancel control, has no default accept action, and suppresses Enter/Return on the dangerous approval button. The final action requires all three separate confirmations and the existing independent Windows approval account. Button-press scopes bind the actual controller/lifetime/token to the eventual click; merely opening the dialog does not request approval, consume credentials or retire monitoring.

The UI's countdown is a conservative display only: it does not authenticate a source, extend/restart the original native 30-second budget or create permission. Accounts, complete context18/binding7-or-9, actual reservation maps, transport quiet, single-use consumption and final effects remain under the native backend gates described below. Known released, known still held and unknown/null disposition stay distinct; local closure is never STOP/LAND/DISARM, remote control release or `Completed`. No compile, tests, scripts, application rendering, authentication/business API/helper or device execution was performed.

## Scope and non-goals

`FleetMissionObservationClose` is a native, read-only-current backend workflow. The 330–334 backend batch did not add a UI button; the 335–339 source integration above supersedes that historical UI status without changing native authority. Ending monitoring is **not** a vehicle STOP, LAND, DISARM, remote control release, verified physical state or `Completed` result. The aircraft may continue flying. Only the actual Run and its original Startup owner's local reservation UUIDs are in scope; another owner's lease must never be released.

The public entries are `requestReview(actualSources, expectedStartupId, expectedRunId, operatorConfirmed)`, `approveAndClose(reviewId, monitorStopConfirmed, localControlReleaseConfirmed, aircraftMayContinueConfirmed)` and `cancelReview(reviewId)`. Both request and final close return bounded public maps. Cancel cancels only this review, never monitoring or flight.

## Actual sources and frozen review

The caller supplies exactly four actual QObject sources: `session`, `roles`, `startupSeries`, `authorizationOwner`. The workflow casts the real Session, RolePolicy and StartupSeries types, obtains the unique current Transaction only through that actual Series' `previousStartup()`, and never finds an owner by an ID or restored snapshot. The expected startup/run IDs must match the actual private Transaction close context.

The private native context has exactly 18 fields: `schemaVersion`, `startupId`, `transactionEpoch`, `transactionGeneration`, `deploymentId`, `runId`, `executionObservationTaskId`, complete `binding`, ordered `targetVehicleIds`, `startupState`, `runReservationCurrentlyHeld`, `startupReservationCurrentlyHeld`, `reservationDisposition`, `flightMayContinue`, `missionResultVerified`, `sourcesMayBeUnavailable`, `targets`, `localReservationState`. Its schema version remains 1 because this new batch has not been released. Binding keeps the existing full seven fields or all nine including the paired input/review generations. Each target contains the fixed 11-field, bounded last-observed diagnostic row supplied by the actual Transaction, with actual Qt Int IDs and the original MODE-step UUID. It does not contain raw frames or coordinates and does not certify current telemetry/physical state.

`localReservationState` freezes the actual owner-map occupancy and authority revocation, not merely two effective-permission booleans. It has exactly `run` and `startup`; each entry is exactly `{owner, occupiedVehicleIds, authorityRevoked}`. Owner must be the corresponding canonical run/startup UUID, occupied IDs are 0–32 strictly ascending, unique actual Qt Int IDs in 1–255, and `authorityRevoked` is an actual bool. Both lists must be subsets of the original target assignment and cannot overlap. An unexpected/out-of-scope occupancy snapshot is rejected rather than silently expanding the reviewed release scope. The full snapshot participates in the frozen context and approval binding hash, so a same-true membership change or revocation change invalidates the old review.

Both `CurrentlyHeld` fields mean that at least one actual owner-map entry exists anywhere for that exact UUID, including a safety-revoked owner; they must agree with the corresponding frozen list's nonemptiness. They do **not** mean valid authorization, a transferable lease, dispatch permission or permission to reuse a vehicle. False is not inferred from `missionDeploymentOwns` rejecting a revoked/incomplete assignment. The workflow does not authorize execution based on either bool.

Separate private `observationCloseSourceObjects` evidence freezes actual Run, Swarm and Orchestrator QPointers in addition to Session, RolePolicy, Series, Transaction and authorization owner. These three pointers are reobtained and compared by the pure native fence, but never exposed in public state or the four-source QML bundle. Frozen vehicle/mission objects or telemetry may be unavailable; the actual primary owner objects cannot be replaced. An adoption failure leaving the original Startup's local reservation held may still be explicitly reviewed. Transaction's native gate separately requires a quiet terminal transport/native stack.

The fixed 30-second monotonic deadline begins during the initial request, before context/account/callback checks. It includes human review and the entire Windows credential modal; no callback, approval, retry or consume restarts it. An active/consuming/committing workflow cannot be overwritten by another request. A new review gets a fresh UUID and nonwrapping generation under the actual workflow's lifetime epoch.

## Independent account and one-use consumption

Request only captures and checks the actual primary identity and exact nine-field RolePolicy receipt for `task.observation.close`; it does not prompt, consume authentication, retire monitoring or release a reservation. The actual identity actor/role must match that policy receipt, with `allowed=true` and `requiresSecondApproval=true`. The role receipt alone never authenticates an account.

Final close requires all three explicit confirmations. The native Session then authenticates a different TokenUser SID with the dedicated `task.observation.close.approve` action. Its binding is SHA-256 of the entire bounded object `{reviewUUID, workflowEpoch, generation, context, identity, role}`, not a plan-only hash or old start/upload approval. A short fixed operation description and the native prompt state that aircraft may keep flying and that this is no STOP/LAND/DISARM/Completed operation. Primary/approver receipts and SIDs remain private.

Before final consumption the workflow rechecks actual objects/threads, original deadline/generation/state, Series' actual current Transaction, exact context, native role/current identity/WTS and dedicated approver receipt. Both authorization-owner QML hooks (`fleetObservationCloseSourcesMatch(actualWorkflow, bundle)` and `fleetObservationCloseContextAllowed(actualWorkflow, context)`) must allow the frozen scope. After every OS/callback boundary actual native ownership/context and the original deadline are checked again. The Session's own modal `changed` signals are not mistaken for applicant replacement; actual identity is revalidated after that call.

The Session's private `consumeObservationCloseAuthentication` burns the pending approver credential once and returns only an immediate bool—no stored grant, lease or reusable proof. Its calls to `authenticationBindingCurrent` use a **pure passive** workflow checker: exact frozen identities/hash, actual Session/object threads, consuming state, per-consumption nonce, generation and original deadline. That checker does not invoke OS authentication, native context getters, QML callbacks or Session receipt getters, including after Session has already burned its internal pending receipt.

All QML and workflow OS gates finish before this consume. Afterwards only a final pure native Series/context/owner/role check is allowed. The workflow marks authentication consumed and state `committing` before its single call to the actual Transaction's `commitObservationClose`. Cancellation, expiry, a stale source or a failed final fence cannot restore credentials, old permissions or old approval. There is no automatic close on expiry, source loss or timer ticks.

## Effects, lifetime and unknown results

Commit may synchronously drain/publish and destroy this service or its Transaction. The result captures QPointers and local return facts; a returned retirement fact survives loss of the UI/service object and is never described as rolled back. No member of a destroyed service is subsequently read.

The separate native post-commit disposition has exactly four bools: `monitoringRetired`, `runReservationCurrentlyHeld`, `startupReservationCurrentlyHeld`, `localReservationsReleasedVerified`. It uses actual owner-map occupancy, independently of effective authorization/revocation. The last is true only when neither exact owner has any remaining actual map entry. After monitoring retirement, a valid disposition that still shows actual occupancy is `closed-local-reservations-held`, not an unknown result; the reason explicitly preserves that remaining occupancy without restoring authority. Only an unavailable/malformed post-state is `closed-release-unknown`, not false and not a claim of successful release. This diagnosis never retries release or restores credentials. Even verified local release does not verify remote control, stopped flight, mission completion or that these members can already be reassigned.

Public state contains the review ID/epoch/generation, remaining fixed budget, frozen context, role label, fixed risk warning, the three confirmations and retirement/local-release facts. It never includes primary/approver SID, account receipts, raw credentials, caller-supplied free text or QObject pointers. Source freshness/state, physical state, remote control release, mission result/completion and flight-command release remain unverified/false. Notifications are queued and coalesced; current inspection has no OS checks, side effects or automatic execution.
